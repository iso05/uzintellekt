UzIntellekt — Административная панель

Developer-ready specification · новый изолированный SPA на стеке dashboard/ · единый дизайн (токены + shared/ui)

Обзор

Административная панель UzIntellekt — внутренний инструмент НКО для сотрудников с ролью ADMIN. Она даёт обзорную аналитику по системе (works / users / moderation / storage), обслуживает ежедневный конвейер модерации работ (approve / reject), управление пользователями, а также файлами и договорами. Панель — отдельное Vite/React-приложение, изолированное по сборке и деплою от пользовательского dashboard/, но переиспользующее его дизайн-токены, компоненты shared/ui и HTTP-инфраструктуру shared/api. Старое приложение Admin-panel/ удаляется.

Ядро продукта: дашборд — стартовый обзорный экран, модерация работ — то, где админ проводит основное рабочее время. Оба входят в v1.

Требования

Функциональные

  1. Аутентификация: собственная страница входа по логину/паролю (POST /api/v1/auth/login); после входа проверка role === 'ADMIN', иначе доступ запрещён и сессия сбрасывается.
  2. Дашборд (аналитика): агрегированные метрики works/users/moderation/storage; временные ряды (Recharts) с выбором периода и гранулярности; топ-контрибьюторы и топ-потребители хранилища.
  3. Модерация работ: grid работ с фильтром по статусу (очередь = UNDER_REVIEW), карточка работы с деталями и вложениями, скачивание файлов по presigned-URL, решение APPROVE/REJECT (с обязательной причиной при отклонении).
  4. Работы от имени пользователя: создание, редактирование и отправка работы на review за пользователя (admin-works).
  5. Управление пользователями: grid с фильтрами/сортировкой/пагинацией, просмотр карточки, ручное создание, редактирование (включая назначение роли), блокировка и активация.
  6. Файлы: сводный grid всех вложений с квотами и статусами; скачивание и удаление файлов конкретной работы.
  7. Договоры: загрузка legacy-договора за пользователя, подписание договора от имени пользователя, скачивание файла договора.
  8. Локализация: интерфейс на 4 языках (uz-Cyrl / uz / ru / en), переключатель языка, как в dashboard.

Нефункциональные

  • Единый дизайн: строго дизайн-токены + shared/ui. Никаких выдуманных палитр или самодельных дублей существующих компонентов (UI-контракт проекта).
  • Устойчивость сети: переиспользуется shared/api/http.js — прозрачный refresh токена (single-flight), backoff на 429 для GET, обработка блокировки аккаунта, дедуп одинаковых GET.
  • Кэш grid: TTL-LRU кэш (cachedGridGet), инвалидация по префиксу эндпоинта после мутаций.
  • Форматы дат: дашборд-эндпоинты принимают и возвращают dd.MM.yyyy; ответы кэшируются на бэкенде ~60с. Единый рендер дат на фронте (как договорено в проекте).
  • Ошибки: error boundary на уровне роутов, единый формат ошибок из err.apiError.errorMessage, тосты (sonner), пустые/loading/skeleton-состояния.
  • Доступ: все данные тянутся под bearerAuth JWT; ни один экран не доступен без валидного ADMIN-токена.

Архитектура

Панель — статический SPA (React 18 + Vite), собираемый отдельно и раздаваемый nginx. Слои по Feature-Sliced Design, как в dashboard/: app (роутинг, провайдеры) → pages → widgets → features → shared. Инфраструктурные слои (shared/ui, shared/api, shared/config, shared/lib, i18n) копируются из dashboard, чтобы гарантировать идентичный дизайн и поведение сети. Графики строятся на Recharts. Приложение обращается к Uzintellekt API (Spring Boot) через JWT; файлы скачиваются напрямую из объектного хранилища по presigned-URL, выдаваемым API.

Технологический стек

  • React 18.2 + React Router 6 + Vite 5
  • Tailwind CSS 3.4 + tokens (tailwind.config.js из dashboard), class-variance-authority, tailwind-merge
  • Radix UI primitives + shadcn-style shared/ui (копия из dashboard)
  • Recharts — графики дашборда (Line / Bar / Pie)
  • i18next + react-i18next (4 языка), lucide-react иконки, sonner тосты
  • Vitest + Testing Library + happy-dom для тестов

Модель данных

Backend владеет данными; панель их читает и мутирует через API. Ниже — ключевые сущности, которыми оперирует админка, с реальными полями и enum-значениями из OpenAPI.

Хранение

PostgreSQL — через API (панель не ходит в БД напрямую). Файлы вложений — в объектном хранилище (S3-совместимом); загрузка/скачивание через presigned-URL, выдаваемые эндпоинтами work-files. Клиентское состояние — только JWT в token-storage (localStorage) и TTL-LRU кэш grid-запросов в памяти.

API — используемые эндпоинты

Все под bearerAuth. Grid-эндпоинты принимают gridRequest — URL-encoded JSON { page, size, sort, filters } — и возвращают { totalPages, totalItems, items[] }. Дашборд-эндпоинты используют даты dd.MM.yyyy.

Пользовательский поток — модерация

Главный ежедневный сценарий: вход → дашборд-обзор → очередь модерации → карточка работы с вложениями → решение.

Аутентификация и авторизация

  • Вход: собственная форма (username + password) → POST /api/v1/auth/login → { token, refreshToken, expiresIn, refreshExpiresIn }, сохраняется в token-storage.
  • Гейт ADMIN: после входа GET /api/v1/users/me; если role !== 'ADMIN' — доступ запрещён, токен очищается, показывается сообщение. ProtectedRoute оборачивает все приватные роуты.
  • Сессия: прозрачный refresh (single-flight) до истечения access-токена; при 401 после исчерпания refresh — редирект на login. Логика уже реализована в shared/api/http.js.
  • Блокировка: ответ 401/403 с сообщением о блокировке обрабатывается централизованно (очистка токена, экран «аккаунт заблокирован»).
  • Роли в данных: панель может назначать роли (USER/ADMIN/MODERATOR) через PATCH /admin/users/{id}, но вход в саму панель — только для ADMIN.

Обработка ошибок

  • Единый разбор ошибок API: err.apiError.errorMessage → тост (sonner); статус в err.status.
  • ErrorBoundary на уровне роут-групп — падение экрана не роняет всё приложение.
  • Состояния данных: loading-state / skeleton при загрузке, empty-state для пустых grid, явные сообщения при 429 («сервер занят»).
  • Мутации (decide, block, delete) — без авто-ретрая (исключаем дубли side-effect); ошибка показывается тостом, действие можно повторить вручную.
  • Валидация форм создания/редактирования пользователя и работы — через field-error + серверные ValidationRestError.

План тестирования

Unit-тесты (Vitest)

  • Сборка gridRequest (page/size/sort/filters) и разбор DataGridResponse.
  • Гейт роли: редирект/отказ при role !== 'ADMIN'.
  • Форматирование дат dd.MM.yyyy ↔ отображение; маппинг enum статусов в бейджи/цвета.
  • Трансформация series → данные Recharts; пустые/нулевые ряды.

Интеграционные тесты

  • Модерация: рендер очереди, открытие работы, decide APPROVE/REJECT, инвалидация кэша и обновление списка (мок API).
  • Users: создание, редактирование роли, block/activate — оптимистичные состояния и откат при ошибке.
  • Обработка 401 → refresh → повтор запроса (мок fetch).

End-to-end (smoke, /test-app)

  • Логин ADMIN → дашборд рендерит метрики и графики.
  • Полный цикл модерации одной работы до REGISTERED.
  • Проверка на desktop / tablet / mobile (адаптив), запрет доступа не-ADMIN.

Развёртывание

  • Сборка: vite build → статический dist/; отдельный артефакт и деплой (не связан с dashboard).
  • Раздача: nginx со SPA-fallback (try_files … /index.html) и прокси /api на API (:8080).
  • Конфиг: API_BASE_URL и родственные через .env / shared/config/env, как в dashboard.
  • Окружения: внутренняя сеть (Tailscale 100.x) для стейджа; отдельный поддомен/путь для админки в проде.

Открытые вопросы

  • Как заводятся ADMIN-аккаунты (сид в БД / отдельный процесс)? Есть ли восстановление пароля для админов?
  • Точная семантика фильтров gridRequest (операторы, множественные значения) — нужно свериться с реализацией grid на бэкенде.
  • Значения granularity и metric для series-эндпоинтов (day/week/month? какие метрики) — уточнить перечень.
  • Ограничения на legacy-загрузку договоров (форматы, размер) и требуется ли предпросмотр перед подписанием (/contracts/preview).
  • Нужны ли аудит-лог действий админа и экспорт grid (CSV/XLSX) — кандидаты в advanced.
  • Отдельный поддомен vs общий хост с dashboard; политика CORS/куки при собственном login.
  • Роль MODERATOR уже есть в API — планируется ли отдельный вход модератора в будущем (влияет на дизайн гейта).
