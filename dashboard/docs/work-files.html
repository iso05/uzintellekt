Файлы работ и квота хранилища

Доработка дашборда UzIntellekt · спецификация для разработки · 2026-06-30

Обзор

Дашборд участника позволяет регистрировать работы, но не даёт прикреплять файлы — флоу регистрации неполный. Бэкенд добавил presigned-загрузку (work-files) и эндпоинт квоты (storage-quota). Цель доработки — дать участнику загружать, просматривать, скачивать и удалять файлы работы прямо в дашборде, видеть остаток квоты, при этом не показывать сырые статусы и не ронять загрузку на истёкших presigned-ссылках.

Охват этой итерации только участник: work-files + storage-quota. Админские группы (admin-*) и вход по логину/паролю — вне охвата.

Требования

Функциональные

  1. Загрузка файлов по presigned-флоу: init → прямой PUT в хранилище → confirm.
  2. Продвинутый загрузчик: drag&drop, множественная очередь, параллельная загрузка, прогресс по каждому файлу, авто-повторы с backoff, переинициализация при истёкшем uploadUrl.
  3. Список файлов работы: показываются только файлы со статусом UPLOADED (статусы PENDING/DELETED скрыты).
  4. Скачивание файла через download-url (получить ссылку → открыть/скачать).
  5. Удаление файла: UPLOADED — с подтверждением (AlertDialog); EXPIRED-надгробие — сразу, без диалога (объект уже удалён из хранилища, подтверждать нечего).
  6. Валидация перед init: белый список типов (по расширению/MIME) + проверка остатка квоты (sizeBytes ≤ remainingBytes). Отдельного пофайлового лимита размера нет.
  7. Квота хранилища: прогресс-бар used/limit в секции файлов и карточка-стат на главной; пред-проверка остатка перед загрузкой.
  8. Размещение UI: секция файлов в WorkFormPage — редактируемая для DRAFT, read-only (список + скачивание) для несменяемых состояний (submitted/decided), используя существующий флаг isReadOnly.

Нефункциональные

  • Изоляция presigned-PUT: загрузка в хранилище идёт в обход request() — без Authorization и без API_BASE_URL, отдельным XMLHttpRequest (нужен прогресс) на абсолютный uploadUrl с заголовком Content-Type: requiredContentType.
  • Локализация: все строки через i18n (uz / uz-Cyrl / ru / en), размеры — человекочитаемо (КБ/МБ/ГБ).
  • Без сырых enum в UI: статусы и ошибки маппятся в локализованные тексты.
  • Кэш: список файлов и квота инвалидируются после загрузки/удаления (квота — после каждого confirm/delete).
  • Доступность: зона drag&drop с клавиатурным фолбэком (<input type=file>), focus-visible, понятные aria-метки прогресса.

Архитектура

Новый FSD-срез entities/work-file (API + модель) и фича features/work-file-upload (очередь, прогресс, повторы). Виджет widgets/work-files (секция файлов + бар квоты) встраивается в WorkFormPage. Квота на главной — отдельная карточка в widgets/works-stats или соседняя. Только PUT в хранилище идёт мимо общего HTTP-слоя.

Технологический стек

  • React 18 + Vite, FSD, TailwindCSS, Radix-примитивы (shared/ui: Dialog, AlertDialog, Button, Badge, Skeleton, toast).
  • XMLHttpRequest для PUT (нужен upload.onprogress; fetch прогресс отдачи не даёт).
  • i18next (4 локали), существующий кэш shared/api/cache.js.

Модель данных

Сущности на стороне бэкенда; фронт хранит их как есть плюс эфемерное состояние элемента очереди загрузки.

Хранение

Состояние файлов — на бэкенде; объект — в S3/MinIO. Фронт ничего не персистит (очередь живёт в памяти компонента; возобновление после перезагрузки страницы — вне охвата v1).

Пользовательский флоу загрузки

Валидация и ограничения

  • Белый список типов (константа ALLOWED_EXTENSIONS, настраиваемо): на данный момент только документы — PDF, DOC, DOCX. Проверка по расширению до init. Дополнительно бэкенд валидирует сигнатуру содержимого (magic-байты) на confirm.
  • Размер ограничен только остатком квоты: блокируем, если file.size > remainingBytes; при множественной очереди учитываем суммарный размер ещё не подтверждённых файлов.
  • Состояние работы: загрузка/удаление доступны когда isEditableState(workState) — DRAFT или REJECTED (правка REJECTED возвращает в DRAFT). Иначе — read-only список.
  • Статусы файла: показываются UPLOADED (скачать/удалить) и EXPIRED (надгробие «срок хранения истёк — загрузите заново», без скачивания; 3-дневный ретеншен на DRAFT/REJECTED); PENDING/DELETED скрыты.
  • Гейт отправки: кнопка «Отправить на рассмотрение» активна только если у работы есть ≥1 файл UPLOADED (бэкенд иначе вернёт 1022).
  • Дубликаты имён в пределах одной работы — предупреждение, не блок (бэкенд решает финально).

Обработка ошибок

  • Истёкший uploadUrl (403/410 от хранилища либо превышен expirationMinutes): автоматический повторный init и повтор PUT; до N попыток с экспоненциальным backoff.
  • Сбой сети на PUT: элемент очереди → error, кнопка «Повторить»; авто-повтор для transient-ошибок.
  • 422 на init (ValidationRestError): показать пофайловую ошибку под элементом очереди.
  • Орфанные PENDING (init без confirm): не отображаются в списке (фильтр UPLOADED); сборка мусора — на бэкенде.
  • Квота исчерпана: блокировать добавление в очередь, тост + подсветка бара квоты; сообщение «Недостаточно места».
  • Единый формат: ошибки API проходят через существующий request() (маппинг RestError → toast), сырые статусы не показываем.

План тестирования

Юнит-тесты (Vitest)

  • entities/work-file/api: пути/методы запросов; фильтр списка по статусу UPLOADED; PUT идёт мимо request() с верным Content-Type.
  • Валидация: whitelist отклоняет неразрешённый тип; size > remaining блокируется; учёт суммарного размера очереди.
  • Форматирование размеров (bytes → КБ/МБ/ГБ) и расчёт процента квоты.
  • Логика повторов: истёкший URL → повторный init; backoff; лимит попыток.

Интеграционные (Testing Library)

  • Секция файлов: drop файла → элемент очереди → прогресс → появление в списке (моки init/PUT/confirm).
  • Удаление через AlertDialog → файл исчезает, квота обновляется.
  • Read-only режим для несменяемой работы: нет dropzone/удаления, есть скачивание.

E2E / ручная проверка

  • На живом бэкенде: загрузить PDF к DRAFT-работе, скачать, удалить; проверить бар квоты в секции и карточку на главной.

Открытые вопросы

  • Точный whitelist расширений и нужно ли согласовать его с бэкендом (есть ли там свой список).
  • Степень параллельности очереди (например, не более 3 одновременных PUT) — подобрать по нагрузке.
  • Поведение confirm при множественной очереди: батч после всех PUT или по факту каждого (план — по факту каждого).
  • Нужна ли отдельная навигация/маршрут на «просмотр работы», или достаточно read-only WorkFormPage (план — второе).
  • Возобновление загрузки после перезагрузки страницы и chunked/multipart — отнесено в «Продвинутые».
